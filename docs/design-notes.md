# StockFlow（Laravel 版）設計ノート

面談で「どう作ったか・なぜそうしたか・どう確かめたか」を説明するためのメモです。細かい仕様は [docs/spec.md](spec.md)、セットアップと各機能の詳しい説明は [README](../README.md) にあります。

- 受発注・在庫管理の社内業務システム（デモ）です。データはすべて架空です
- [Next.js 版（stockflow-next）](https://github.com/yuya1129t-project/stockflow-next) と同じ業務仕様・同じ REST API 仕様で作っています
- 要件・方針の決定と公開の判断は本人が行い、設計・実装・コードレビュー（Claude と Codex の独立したレビュー）・指摘への対応は Claude Code が行っています。本人は成果物を確認しています

各節は「何を」「なぜ」「どう確かめたか」の順に書いています。

## 1. Laravel の MVC（画面は Inertia＋Vue）

**何を**
- ルート（`routes/web.php`）→ コントローラー（`app/Http/Controllers`）→ サービス（`app/SalesOrders/SalesOrderService.php` など）→ モデル（`app/Models`）の流れです
- 画面（View）は Blade ではなく、Laravel 公式のスターターキットの Inertia＋Vue 3（`resources/js/pages`）です。コントローラーは `Inertia::render('sales-orders/Show', [...])` で、画面に必要な値だけを渡します
- コントローラーは薄くしています。入力の検査は Form Request、権限は Policy、業務の手順（ロック・トランザクション・操作履歴）はサービスに置きます。一覧や集計の読み出しは `…Query` クラス（`app/SalesOrders/SalesOrderQuery.php` など）にまとめています

**なぜ**
- 受注・発注・REST API など、同じ業務の手順を複数の入口（画面と API）から呼ぶためです。手順をサービスに 1 つだけ置けば、画面と API で動きが食い違いません（REST API の受注の登録も、画面と同じ `SalesOrderService::create` を通ります）
- Inertia にしたのは、画面の部品は Vue で作りつつ、ルーティング・認証・権限はサーバー（Laravel）側に残せるからです。API を別に作らずに SPA のような画面にできます

**どう確かめたか**
- 機能テスト（Pest）で、コントローラー経由の要求（画面）と、サービスを直接呼ぶ場合の両方を確かめています（例: `tests/Feature/SalesOrders/SalesOrderTest.php`）
- REST API の受注の登録が、画面で作った受注と同じ採番・金額・操作履歴になることを `tests/Feature/Api/RestApiTest.php` で確かめています

## 2. Eloquent の使いどころ

**何を**
- 普通の読み書き（一覧・詳細・作成）は Eloquent のモデルで書いています。リレーションは `with()` でまとめて読みます（次の「N+1」）
- 在庫の出荷・入荷のように「同時に動いても壊れてはいけない更新」は、あえて Eloquent のモデルの `save()` を使わず、`DB::table('sales_orders')->where('id', $id)->where('status', 'confirmed')->update([...])` のような**条件付きの UPDATE** にしています

**なぜ**
- デッドロックのときにトランザクションをやり直す設計（後述）では、処理（コールバック）が 2 回動きます。外で読んだモデルを中で書き換えて `save()` すると、2 回目は「変更なし」と判断されて UPDATE が出ず、更新が消えることがあります。条件付き UPDATE なら毎回同じ SQL が出ます
- 「更新できた件数」で、同時に処理した 2 本目を見分けられます（件数が 0 なら、もう誰かが出荷済み）

**どう確かめたか**
- 出荷を「読んでから更新」に書き換える変異を入れると、同時出荷のテストが落ちることを確かめています（README「受注」のテスト）
- 出荷がデッドロックで 1 回やり直しになっても、出庫・操作履歴が 1 回分だけ残ることをテストで固定しています（`SalesOrderConcurrencyTest` の「出荷がデッドロックの負け側になっても…」）

## 3. Form Request

**何を**
- 画面からの入力の検査は Form Request（`app/Http/Requests`）で行います。エラー文はすべて日本語です
- `authorize()` でも Policy を呼び、ルートの `->can(...)` と合わせて権限を二重に確かめます
- 金額（小計・税・合計）や受注日は**入力として受け取らず**、サーバーで明細から計算します

**なぜ**
- 入力の形（必須・数値・桁数）の検査をコントローラーから追い出し、コントローラーを読みやすくするためです
- 金額を画面から受け取ると、改ざんされた金額で保存できてしまいます。画面の計算はあくまで表示用です

**どう確かめたか**
- 入力検証のテストは、項目ごとに「どの値で、どの日本語のエラーになるか」をデータセットで並べています（例: `SalesOrderTest` の「入力検証」）
- 小計・税・合計を細工して送っても無視され、サーバーで明細から計算した金額で保存されることを確かめています（`SalesOrderTest` の作成）

## 4. Policy と Gate（権限）

**何を**
- 権限の表は `app/Auth/Permission.php` の 1 か所だけです（spec §2 の表と同じ）。`AppServiceProvider` でこの表を Gate のアビリティとして登録し、ルートで `->can(Permission::OrderEdit)` のように検査します
- モデルごとの判断（例: 自分自身は無効化できない）が要るところは Policy（`app/Policies`）にし、Policy の中でも同じ表を使います
- 画面のボタンの出し分けにも同じ表（ログイン中のユーザーの権限の一覧）を使います。ただしボタンを隠すのは補助で、**サーバー側で必ず 403 にします**

**なぜ**
- 権限の定義が複数の場所に散ると、画面では隠れているのに API では通る、といった食い違いが起きます。表を 1 つにすれば、ルート・Policy・画面が同じ答えを返します

**どう確かめたか**
- 機能テストで、3 ロール × 9 つの権限（27 通り）について、Gate の判定・ルートの検査・コントローラーの検査が権限表どおり（許可は 200、それ以外は 403）であることを確かめています（`tests/Feature/Auth/AuthorizationTest.php`）
- ブラウザテストで、viewer の画面に編集のボタンがないことを、**同じ画面を staff で開いてボタンがあること（対照）と並べて**確かめています。ボタンの名前が変わったときに、viewer の側だけ素通りしないようにするためです。直接 URL を開いたときの 403 も、staff が同じ URL を開けることと並べています（`tests/Browser/PermissionsTest.php`）

## 5. Job と Queue（発注点割れの通知）

**何を**
- 在庫が発注点を下回ったら、Slack の Incoming Webhook 形式で通知します。送信は Job（`app/Jobs/SendReorderPointNotification.php`）にして、キューで送ります
- Job は `ShouldQueueAfterCommit` です。**トランザクションが確定してから**キューに入ります。呼び出し側も、在庫のトランザクションが終わった後で投入しています
- 送信に失敗しても、出荷などの業務処理は取り消しません。失敗は操作履歴に記録します。再試行は「届いていないことが確かなとき」（接続の前の失敗・429）だけです

**なぜ**
- 外部への送信は遅かったり失敗したりします。画面の応答を待たせない・業務の確定に巻き込まないために、キューに分けました
- トランザクションの中で送ると、あとで取り消された出荷の通知が届いてしまいます
- タイムアウトや 5xx は、相手が受け取って投稿した可能性があるので、送り直すと二重の通知になります

**どう確かめたか**
- `Http::fake` で送信先を差し替え、送る内容・タイムアウト・リダイレクトをたどらないこと・失敗の記録を確かめています（`tests/Feature/ReorderNotifications`）
- 「出荷のトランザクションの中で投入する」「`ShouldQueueAfterCommit` を `ShouldQueue` にする」変異で、テストが落ちることを確かめています

## 6. Sanctum（外部向け REST API のトークン）

**何を**
- `/api/v1` は `Authorization: Bearer <token>` で認証します。トークンは admin がユーザーごとに発行し（表示は発行時の 1 回だけ。DB にはハッシュ）、失効できます
- Sanctum の「SPA の Cookie 認証」は使わず、**Bearer トークンだけ**で通します（`app/Users/ApiTokenAuth.php`）。失効・持ち主の無効化は毎回確かめます
- 権限はトークンの持ち主のロールで、画面と同じ Gate で判定します

**なぜ**
- 外部のシステムから呼ぶ API なので、画面のログインの Cookie で API が通る必要はありません。Cookie でも通ると、CSRF などの考えることが増えます
- 失敗の理由（トークンがない・形式違い・失効済み・持ち主が無効）を区別せず同じ 401 にして、トークンの状態を推測させないようにしています

**どう確かめたか**
- 「ログインの Cookie だけでは 401」「ロールを変えると次の要求から効く」「失効したトークンは 401」などを `RestApiTest` で確かめています
- Sanctum のガードを `web` に変える変異で、テストが落ちることを確かめています

## 7. N+1 をどう避けたか

**何を**
- 一覧の関連（受注の顧客・明細の商品・操作履歴の利用者）は `with()` でまとめて読みます。必要な列だけを選びます（`with('customer:id,code,name')`）
- 現在庫は「入出庫の合計」なので、商品ごとに合計を問い合わせると N+1 になります。そこで `stock_movements` を商品ごとに `SUM` した結果を、1 本の SQL で商品に結合します（`leftJoinSub`。`app/Products/ProductQuery.php`・`app/Stock/StockQuery.php`）
- ダッシュボードの集計も、すべて DB 側の集計で、データの量によらず問い合わせは 7 本です（`app/Dashboard/DashboardQuery.php`）

**なぜ**
- 一覧の件数が増えたときに、問い合わせの回数が件数に比例して増えると、急に遅くなります。在庫は毎画面で使う値なので、特に影響が大きいです

**どう確かめたか**
- 「データを増やしても問い合わせの回数が変わらない」ことをテストで数えています（`ProductIndexTest`・`StockPagesTest`・`DashboardTest` の「N+1 にしない」）

## 8. 在庫引当: 二重出荷と負の在庫をどう防いだか

この業務システムで一番大事なところです。共通の部品 `app/Stock/StockTransaction.php` だけが入出庫を記録します。

**何を**
1. **トランザクション**: 受注の状態の更新・出庫の記録・操作履歴を 1 つのトランザクションで行います。どこかで失敗したら全部取り消します（在庫が 1 品目でも足りなければ、出荷そのものをしません）
2. **行ロック**: 出庫の前に、対象の商品の行を **id の順に** `SELECT … FOR UPDATE` でロックしてから在庫を数えます。同じ商品を扱う処理はここで順番待ちになり、後の処理は先の出庫を含めた在庫で判断します。順番をそろえるのは、2 つの処理が互いのロックを待ち合う（デッドロック）のを避けるためです
3. **READ COMMITTED**: トランザクションの分離レベルを READ COMMITTED にしています。MySQL の既定（REPEATABLE READ）だと、ロックの前に一度読んだ時点の古い在庫が見えてしまい、先に確定した出庫を見落とすことがあります
4. **条件付き UPDATE**: 受注の更新は `UPDATE … WHERE id = ? AND status = 'confirmed' AND updated_at = ?` です。同時に 2 回「出荷」を押しても、2 本目は 1 本目の確定を待ってから条件を見直し、**更新 0 件**になるので二重に出庫しません。`updated_at` も条件に入れて、画面を開いた後にほかの人が変えていたら「競合」として知らせます
5. **再試行**: MySQL には PostgreSQL の `FOR NO KEY UPDATE` がなく、明細の INSERT（外部キーの検査）とぶつかるとデッドロックが起こりえます。デッドロック（1213）のときだけ、処理を丸ごと 3 回までやり直します。ロック待ちのタイムアウト（1205）はやり直さず、「混み合っているため、出荷できませんでした（在庫は変わっていません）」と返します

在庫数の列は持たず、現在庫は入出庫の合計で求めます（spec §3）。在庫の数字と履歴が食い違うことがありません。

**なぜ**
- 「在庫を確かめてから出庫する」を素直に書くと、同時に 2 人が出荷したとき、両方とも確認を通って在庫がマイナスになります。確認と記録の間に、ほかの処理が割り込めないようにする必要があります
- Next.js 版（PostgreSQL）と同じ考え方ですが、MySQL（InnoDB）のロックの違い（`FOR NO KEY UPDATE` がない・既定の分離レベルが違う）に合わせて、READ COMMITTED と再試行を加えました

**どう確かめたか**
- **同時実行テスト**: 2 つの処理を別々のプロセス・別々の DB 接続で本当に同時に走らせます。「後の処理がロック待ちに入った」ことを MySQL の `performance_schema` で確かめてから、先の処理を確定させます（決まった秒数だけ待つ、はしません。待ちに入らなければテストの失敗）
  - 同じ受注を同時に 2 回出荷 → 出庫は 1 回だけ
  - 別々の受注が同じ商品を同時に出荷 → 在庫はマイナスにならず、後の側は「不足」で中止。後の側の受注の状態・更新日時・操作履歴も変わらない
  - 明細の順番が逆の 2 受注を同時に出荷 → デッドロックしない（やり直しも起きない）
  - 出荷がデッドロックで負けた → やり直しの 2 回目で出荷でき、出庫・操作履歴は 1 回分だけ
  - 出荷がロック待ちのタイムアウトになった → やり直さず「混み合っています」。受注・在庫・操作履歴は変わらない
- **変異**: ロックを外す・id の順をやめる・再試行をやめる・REPEATABLE READ に戻す・出荷を「読んでから更新」にする、などを 1 つずつ入れて、該当するテストが落ちることを確かめています（README の各節）
- **ブラウザテスト**: 画面から受注を作成 → 確定 → 出荷して、在庫画面の数字が減ること、在庫が足りないときに不足の表（必要数・現在庫・不足数）が出てステータスが変わらないことを確かめています（`tests/Browser/OrdersTest.php`）

## 9. テストの方針

| 種類 | 何を確かめるか | どこに |
| --- | --- | --- |
| 単体テスト（Pest） | 税計算・ステータス遷移・CSV の読み書き・在庫の計算など、DB を使わない規則 | `tests/Unit` |
| 機能テスト（Pest・実 DB） | 画面・API の要求ごとの結果、権限、入力検証、操作履歴。DB はテスト用の MySQL（`testing`） | `tests/Feature` |
| 同時実行テスト | 別プロセス・別接続で本当に競合させる（上の「在庫引当」） | `tests/Feature/*/…ConcurrencyTest.php` |
| 契約テスト | REST API の実際の応答を、Next.js 版と共通の `docs/openapi.json` で検証する | `tests/Feature/Api/RestApiTest.php` |
| ブラウザテスト（Pest＋Playwright） | 画面からの主な流れ（ログイン・受注 → 出荷 → 在庫・発注 → 入荷・権限・CSV・ダッシュボード・スマホ幅） | `tests/Browser` |

方針として大事にしていること:
- **値まで確かめる**: 「画面が出た」「ボタンがある」だけで終わらせず、在庫の数字・CSV の各列・ダッシュボードの金額まで比べます
- **対照を置く**: 「viewer には出ない」は「staff には出る」と並べて確かめます
- **固定時間の待ちを使わない**: 同時実行は DB のロック待ちを観測し、ブラウザテストは表示が変わるまで待つ確認（上限つき）を使います。たまたま間に合う・たまたま遅れる、で結果が変わらないようにします
- **変異で確かめる**: 大事な一行（ロック・条件・再試行）をわざと壊して、テストが本当に落ちることを確かめます。「テストが通る」だけでは、そのテストが何かを見ているかは分からないためです
- **テストどうしが影響しない**: テストごとに DB を空にし、そのテストが使うデータだけを作ります。同時実行・ブラウザのテストは、テストのトランザクションを張らずに実際に確定させ、前後で全テーブルを空にします

ブラウザテストについて:
- **Pest のブラウザテスト（pestphp/pest-plugin-browser。中身は Playwright）を選びました**。Laravel Dusk ではなくこちらにした理由は、(1) アプリを Pest がテストのプロセスの中で起動するので、別のサーバーを立てたり使い回したりせず、テスト用 DB・ファクトリーをそのまま使える、(2) 機能テストと同じ Pest の書き方で書ける、(3) Next.js 版の E2E と同じ Playwright なので、ブラウザの動きの前提がそろう、の 3 つです（Dusk は ChromeDriver と、別に起動したアプリのサーバーが要ります）
- アプリを同じプロセスで動かすため、要求の間で認証・セッションの状態が残らないよう、要求ごとにリセットしています（`tests/Support/ResetsRequestState.php`。Laravel Octane が要求ごとに行うのと同じ）。これがないと、別のブラウザ（Cookie なし）からでもログイン済みに見えることを実際に確かめました
- ログインの試行回数の制限（1 分に 5 回など）は無効にしていません。数える先はテストごとに作り直すキャッシュで、1 つのテストのログインは多くても 3 回なので、上限に当たりません

## 10. REST API を Next.js 版と同じ OpenAPI で実装した方法

**何を**
- `docs/openapi.json`（OpenAPI 3.1）は Next.js 版と同じファイルで、**こちらでは変更しません**。これを正として実装しました
- エラーは RFC 9457（`application/problem+json`）、一覧は `{ data, meta: { page, perPage, total } }` で、Next.js 版と同じ形にしています
- 契約テストは、実際の応答を JSON Schema 2020-12 の検証器（opis/json-schema）で `openapi.json` と照らし合わせます。項目の過不足・型・null の可否・日付の形式・範囲まで見ます

**なぜ**
- 同じ仕様を 2 つの言語で実装するとき、「だいたい同じ」では外部のシステムが片方でだけ動かなくなります。仕様書を機械で照合できる形（OpenAPI）にして、テストで毎回突き合わせるのが確実です
- OpenAPI の検証ライブラリには 3.0 前提のものが多く、3.1 の `type: ["string", "null"]` を正しく扱えないことがあるので、JSON Schema 2020-12 の実装に任せる薄い仕組みにしました

**どう確かめたか**
- 全部の応答（成功・エラー）を検証に通し、最後に「定義した応答（パス × メソッド × ステータス、25 通り）をすべて一度は実際に返した」ことを確かめています
- 検証器そのものが食い違い（項目の追加・必須の欠落・日時の形式など 17 通り）を実際に見つけることも、単体テストで確かめています

## 12. 開発の進め方

1. **Issue**: 1 つの Issue（GitHub Issues）に、やること・受け入れ条件を書きます
2. **ブランチと PR**: 1 Issue = 1 ブランチ = 1 PR です。main に直接 push しません
3. **独立したレビュー 2 本**: PR ごとに、Claude と Codex がそれぞれ別々にレビューします（Codex が使えないときは Claude で代替します）。指摘は must／should／nit に分け、対応した内容を PR に書きます。見送った nit は次の Issue に申し送ります（この Issue #13 のテストの整理も、その申し送りです）
4. **CI**: GitHub Actions で、Pint（整形）・Larastan（静的解析）・Pest（MySQL に対して）・フロントの lint と型チェック・ビルド、ブラウザテストを実行します。緑になってからマージします
5. **マージ**: レビューの指摘への対応と CI が済んだらマージします

役割分担: 要件・方針の決定と公開の判断は本人が行い、設計・実装・コードレビュー（Claude と Codex の独立したレビュー）・指摘への対応は Claude Code が行っています。本人は成果物を確認しています。

## 13. 面談で聞かれそうな質問と答えの例

**Q. 在庫数を列で持たずに、毎回合計するのはなぜですか？遅くなりませんか？**
A. 在庫の数字と入出庫の履歴が食い違わないようにするためです。列で持つと、履歴と列の両方を正しく更新し続ける必要があります。合計は商品ごとの `SUM` を 1 本の SQL で結合するので、商品の数だけ問い合わせることはありません。データがもっと増えたら、日ごとの締めの値を持つなどの工夫を考えます。

**Q. 同時に 2 人が出荷ボタンを押したらどうなりますか？**
A. 2 本目は 1 本目の確定を待ってから「まだ確定済みか」を条件付き UPDATE で確かめ、更新 0 件になるので出庫しません。画面には「出荷済のため変更できません」と出ます。別々の受注が同じ商品を同時に出荷した場合も、商品の行ロックで順番待ちになり、後の側は最新の在庫で判断します。どちらも、本当に 2 つのプロセスで同時に走らせるテストで確かめています。

**Q. Next.js 版と Laravel 版で、作り方がいちばん違ったところは？**
A. DB のロックです。Next.js 版は PostgreSQL、Laravel 版は MySQL で、MySQL には `FOR NO KEY UPDATE` がなく、明細の INSERT とぶつかるとデッドロックが起こりえます。そこで、デッドロックのときだけ処理を丸ごとやり直す仕組みと、明細を書く側が先に商品の共有ロックを id の順にまとめて取る決まりを加えました。分離レベルも READ COMMITTED にそろえています。

**Q. テストが不安定（たまに落ちる）にならないよう、何をしましたか？**
A. 決まった秒数だけ待つ書き方をしていません。同時実行は「後の処理がロック待ちに入った」ことを DB で確かめてから進め、ブラウザテストは表示が変わるまで待つ確認を使います。実際に、全体を流したときだけ落ちるテスト（ファクトリーが作る商品コードと、テストで決め打ちしたコードがまれに重なる）や、ロックを得る順番に頼っていたテストを見つけて直しました。

**Q. Claude Code を使った開発で、品質はどう担保していますか？**
A. 1 つの Issue を 1 つの PR にし、PR ごとに Claude と Codex の独立したレビューを 2 本通し、CI が緑になってからマージしています。レビューでは、コードを読むだけでなく実際の DB で再現して確かめた指摘もあります。テストは「わざと壊すと落ちる」ことまで確かめています。要件・方針の決定と公開の判断は本人が行い、成果物は本人が確認しています。

**Q. N+1 はどう見つけて、どう防ぎますか？**
A. 一覧は関連を `with()` でまとめて読み、在庫のような集計は SQL の集計を結合して 1 本で取ります。テストでは、データを増やしても問い合わせの回数が変わらないことを数えて確かめています。
